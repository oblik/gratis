# Gratis CMS

## What it is

A content editor for static sites that runs with no servers, no build pipeline and no third-party CMS. The site is plain files in an S3 bucket, served through Cloudflare. The admin is a single-page app that lives in the same bucket. When an editor changes something, their browser re-renders the affected pages and writes them straight back to the bucket.

The browser does the job a build server or an application server would normally do. Hardware is fast, browsers are powerful, and web standards are stable and backwards-compatible, so this is a reasonable place to put the logic.

## Who it's for

Gratis is for the long tail of tiny sites that a developer builds once and then wants to stop thinking about: the coffee shop down the street, a personal blog, a one-page portfolio, a club or a small practice. The site owner needs to change a heading, update opening hours, swap a photo or add a menu item without calling the developer. Nobody needs drafts, workflows, approval chains or a content API.

Explicit non-goals:

- Drafts, scheduling, review workflows, previews
- Relations between content types, taxonomies, search
- Large sites (hundreds of pages) or high-frequency editing by many people
- Sites that handle payments, accounts or personal data
- "Top-notch" security. Gratis accepts a modest security compromise in exchange for having no moving parts. See [Authentication](#authentication).

The day a site needs any of the above, the honest answer is "use a real CMS", and Gratis should make that easy rather than tempting you to bolt features on.

## Why

Every existing option for giving a non-technical person an editor on a static site depends on something that rots:

- Git-based CMSs (Decap, Sveltia, Pages CMS) commit content and then rely on a build pipeline. GitHub Actions break on dependency bumps; Node versions go out of support.
- Serverless functions need runtime upgrades every couple of years.
- Hosted CMSs raise prices, get acquired or shut down.
- A classic CMS on a VPS needs patching forever.

Gratis's bet is different: depend only on things that already have, or can reasonably be expected to have, a multi-decade lifespan.

- Object storage behind the S3 API. S3 itself has twenty years of unchanged API, and the S3 API is now a de facto standard (R2, Backblaze, Tigris, MinIO), so the bucket is portable with `rclone sync`.
- A CDN for TLS and caching.
- The browser, which is the most backwards-compatible runtime that exists.
- Plain HTML, CSS, JS and JSON files.

A Gratis site has no scheduled maintenance. If nobody touches it for ten years, it keeps serving and it keeps being editable. The only code that can break is Gratis's own renderer, and that risk is bounded by design (see [Consistency and recovery](#consistency-and-recovery)).

## Architecture

### Components

| Component | Role | Initial target | Later |
|---|---|---|---|
| Static site generator | Produces the site and the page templates | Astro | Next.js and others (harder, see [Roadmap](#roadmap)) |
| Object storage | Holds the built site, templates, content, uploads and the admin SPA | AWS S3 | R2 or any S3-compatible store |
| CDN | TLS, custom domain, caching in front of the bucket | Cloudflare | CloudFront and others |
| Admin SPA | Editor UI plus the renderer, served from the bucket at `/admin/` | | |

Nothing else. No application server, no functions, no database, no identity provider. The only piece of Gratis code that runs anywhere is the SPA in the editor's browser (and the same renderer in Node at deploy time).

### Bucket layout

```
/                       built site (public)
/admin/                 the Gratis SPA (public, static)
/uploads/               editor-uploaded files (public)
/_gratis/content.json   all site content, raw
/_gratis/schema.json    field definitions, generated by the SSG adapter at build time
/_gratis/templates/     one HTML template per route template, generated at build time
/_gratis/auth/          per-editor encrypted credential blobs
/_gratis/history/       snapshots of content.json (optional; S3 versioning covers this)
```

### Content model

A single `content.json` holds everything, split into sitewide fields and per-page fields:

```json
{
  "sitewide": {
    "title": "My Site",
    "footerText": "Copyright 2026"
  },
  "pages": {
    "/": {
      "_template": "home",
      "heading": "Hello!",
      "subheading": "Welcome to my site!"
    },
    "/about-us": {
      "_template": "about",
      "address": "San Francisco, CA",
      "contacts": [
        { "email": "john@example.com" },
        { "email": "jane@example.com" }
      ]
    }
  }
}
```

The schema (field names, types, which template a page uses, which fields are lists) is declared in the Astro project and emitted to `schema.json` at build time, so the SPA can render a form for it without any configuration of its own.

Supported field types are deliberately few: short text, long text / markdown, image, link, boolean, and a repeater (a list of a fixed sub-schema, one level deep). That covers the target audience; anything richer is out of scope.

### Templating: DOM markers, not string replacement

Pre-rendered HTML can't be edited by find-and-replace. The same string appears HTML-escaped in the body and differently escaped in `<title>`, meta tags and JSON-LD, and lists change the structure of the DOM. So Gratis doesn't treat a page as a string. The SSG adapter emits a template per route in which editable regions are marked with data attributes, and the renderer manipulates it as a DOM.

In the Astro project the developer uses Gratis helpers:

```astro
---
import { field, each } from 'gratis/astro';
---
<h1 {...field('heading')}>{content.heading}</h1>

<ul {...each('contacts')}>
  <li><a {...field('email', { attr: 'href', prefix: 'mailto:' })}>{item.email}</a></li>
</ul>
```

The build produces, in the template file:

```html
<h1 data-gratis-field="heading">Hello!</h1>
<ul data-gratis-each="contacts">
  <li><a data-gratis-field="email" data-gratis-attr="href" data-gratis-prefix="mailto:">john@example.com</a></li>
</ul>
```

Rendering is then a small, pure function `render(template, content) -> html` that:

1. Parses the template with `DOMParser`.
2. For each `data-gratis-field`, sets `textContent` (or the named attribute). Escaping is handled by the DOM, never by hand.
3. For each `data-gratis-each`, keeps the first child as the item template, clones it once per item, and recurses.
4. For `data-gratis-if`, removes the element when the field is falsy.
5. For markdown fields, renders markdown to DOM nodes in the browser.
6. Serializes back to HTML.

Because it's a pure function of `(templates, content.json)`, the whole site can be regenerated from scratch at any time, in the browser or in Node. That property is what makes everything else safe.

Astro is the right first target because its default output is plain HTML with no hydration payload: the template is the page. Frameworks that ship a serialized data payload alongside the HTML (see [Roadmap](#roadmap)) need the same content written in a second place.

### Edit flow

1. Editor opens `/admin/`, logs in (see [Authentication](#authentication)).
2. SPA fetches `schema.json` and `content.json` and renders the form.
3. Editor changes `heading` on the home page and saves.
4. SPA consults the dependency graph: which pages use the changed fields? A page field affects one page; a sitewide field (navbar, footer) affects every page.
5. For each affected page, SPA fetches its template, renders it with the new content, and `PUT`s the resulting HTML to the page's path.
6. SPA writes `content.json` back with a conditional write.

Creating a page is the same flow with a new entry in `content.json`; deleting one is a `DELETE` plus a `content.json` update.

Fan-out on sitewide fields is real overhead (a 30-page site re-renders 30 pages), and it's accepted: Gratis is for sites where that is a few seconds of work in a browser tab.

### File uploads

Uploads are ordinary `PUT`s to `/uploads/`. Files get a content-hashed or UUID name so a replaced image never collides with a cached one. Image fields store the path.

### Caching and the CDN

Cloudflare proxies the S3 website endpoint. The site needs no cache purging, ever:

- Cloudflare doesn't cache HTML by default, and every HTML page and `content.json` is uploaded with `Cache-Control: no-cache`, so edits are visible on the next request.
- Astro content-hashes its CSS and JS filenames; uploads have unique names. Those can be cached forever.

Writes never pass through the CDN: the SPA talks to the S3 REST endpoint directly over HTTPS. The S3 website endpoint is HTTP-only, so Cloudflare runs in Flexible SSL mode toward the origin; that is acceptable for public site content and irrelevant to the admin path. Optionally the bucket policy limits anonymous `GetObject` to Cloudflare's IP ranges so the bucket can't be read around the CDN.

### Consistency and recovery

There are no transactions, so the design leans on cheap guarantees:

- Optimistic locking: `content.json` is written with `If-Match` on the ETag it was read with. Two editors saving at once get a conflict instead of silently overwriting each other.
- Pending marker: before fanning out, the SPA writes `content.json` with a `_pending` list of pages still to render; it clears the list last. If the tab dies mid-save, the next admin session sees the marker and finishes the job.
- Re-render everything: a button in the admin regenerates every page from `content.json`. Any corruption caused by a renderer bug is fixed by fixing the bug and pressing the button.
- Undo: S3 bucket versioning is on, so every overwrite is recoverable. The SPA also keeps a short history of `content.json` snapshots for stores without versioning.
- Deploys re-render: when the developer deploys new templates, the deploy step runs the same renderer in Node against the live `content.json`, so content is never lost or stale after a template change. Deploys must never overwrite `content.json`, `/uploads/` or `/_gratis/auth/`.

## Authentication

This is the part that forces the design, so it's worth being precise about.

A bucket can verify exactly one kind of credential: a SigV4 signature made with an IAM access key. There is no session, no cookie, no password it understands. So every serverless auth scheme reduces to one question: how does the editor's browser come to hold an IAM key? Gratis answers it with the pattern password managers use: a password that unlocks an encrypted credential.

### Setup

- The developer creates one IAM user per editor, with an inline policy allowing `GetObject`, `PutObject`, `DeleteObject` and `ListBucket` on this one bucket and nothing else, and generates an access key pair.
- For each editor, `/_gratis/auth/<username>.json` stores that key pair encrypted with AES-GCM under a key derived from the editor's password with PBKDF2 (WebCrypto, high iteration count; Argon2id via a small wasm module is a later option).

### Login

1. SPA fetches the editor's blob.
2. Derives the key from the password, decrypts the key pair, keeps it in `sessionStorage`.
3. Signs every storage request directly with `aws4fetch` or equivalent. No credential is ever sent anywhere except in the form of a signature to S3.

### User management

The super user (first editor, created by the developer) can add editors from the SPA: the developer supplies a key pair, the super user sets a password, the SPA writes the blob. Removing an editor is deleting the blob and deactivating their key in IAM. One key per editor means revocation is a single click with no re-encryption.

### Threat model, stated plainly

What this protects against: an attacker without an editor's password cannot write to the bucket. The bucket is never publicly writable. No bearer token travels in a URL or header.

What it doesn't:

- The auth blobs are publicly readable (they're on a public site; a WAF rule on the path is trivially bypassed), so a weak password can be brute-forced offline. The defence is a high KDF cost and an enforced password minimum (12+ characters). This is the main accepted compromise.
- No MFA, no lockout, no audit trail beyond S3 access logs / CloudTrail.
- An editor can, by design, upload anything to the site, including scripts. Editors are trusted.

This is the right level for a bakery's website. It is the wrong level for anything handling money or personal data, and the docs say so.

### Variant: device-bound, nothing stored

For an even smaller surface, the developer can onboard an editor with a one-time link `/admin/#setup=<encrypted-keys>`. The fragment never reaches a server or a log; the SPA stores the keys in that device's IndexedDB. No blob exists anywhere. The trade-off is that a new device needs the developer again.

### Why not something stronger

Cognito, Cloudflare Access, a tiny Worker or a Lambda would each fix the weaknesses above, and any of them could be offered as an optional adapter later. They are not in the core because each is another service to configure and another thing that can change under the site. The core promise is "a bucket, a CDN and a browser"; auth has to fit inside that.

## Setup

`gratis init` does, or prints exact instructions for:

1. Create the bucket with static website hosting, versioning, a CORS rule allowing `GET`/`PUT`/`DELETE` from the site origin with `ETag` exposed, and a public-read bucket policy (optionally restricted to Cloudflare IPs).
2. Create the IAM user(s) and keys.
3. Upload the built site, templates, schema, an initial `content.json`, the admin SPA and the super user's auth blob.
4. Point a Cloudflare DNS record at the website endpoint with the proxy on, SSL mode Flexible.

The developer experience of this step matters as much as the editor. If setup is an hour of console clicking, nobody reaches the "no maintenance forever" part.

## Roadmap

The core is deliberately small. Extension points, in rough priority order:

### Other static site generators

The adapter contract is: emit DOM-marked templates and a `schema.json` at build time, and provide helpers for marking fields. Any SSG whose output is plain HTML fits easily (Eleventy, Hugo).

Next.js is harder and should come later, if at all. Static export embeds an RSC/hydration payload in each page that duplicates the content in JSON-escaped form, and client-side navigation fetches separate payload files, so a page updated only in its HTML shows stale content on in-app navigation. A Next adapter would have to update those payloads too, or constrain projects to pages with no client navigation.

### Other S3-compatible storage

Because the SPA speaks the S3 API, swapping storage is configuration plus a provider-specific setup page. Known differences for R2: no object versioning (use the `content.json` history snapshots), no `index.html` rewriting on custom domains (needs a Cloudflare Transform Rule or `build.format: 'file'`), per-bucket API tokens instead of IAM users (editors share a token, so revocation means rotation and re-encrypting blobs). R2's advantages are free egress and native HTTPS custom domains without a separate CDN step.

### Other CDNs

CloudFront is the natural fit for S3-only users. Unlike Cloudflare, it caches HTML, so the SPA would need to create invalidations after writes. That works without any new service because editors already hold IAM keys: add `cloudfront:CreateInvalidation` on the distribution to their policy.

### Optional hardening adapters

For clients who need it: Cloudflare Access in front of `/admin/`, or a dependency-free Worker that holds the storage credential and checks sessions, kept strictly out of the serving path so that if it disappears the site stays up and only editing stops.

## Open risks

- The renderer is the one piece of code that can corrupt a site. Mitigated by purity, versioning and the re-render button, but it needs a thorough test suite against real Astro output.
- Markdown rendering in the browser must produce the same output as at deploy time in Node. Use one implementation for both.
- Scope creep. The first request for drafts or previews is the moment to say no.
